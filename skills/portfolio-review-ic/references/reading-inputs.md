# Reading the portfolio

<!--
  Why this file exists: the most common way an AI portfolio review goes wrong is
  not bad judgment, it is judging a portfolio it only partially read, then
  writing as if it had read all of it. Everything here is about knowing what
  was actually seen and saying so.
-->

## Supported inputs

1. **PDF** (preferred for reliability). Exported decks, PDF portfolios, case
   study exports. Read text and look at the page images: visual quality cannot
   be assessed from extracted text alone.
2. **Website URL**. Personal sites, Framer, Webflow, Squarespace, Next.js and
   similar. Fetch the home page, then follow links to each case study.

Anything else (screenshots, image folders) can be used as a fallback when the
user supplies it, but is not a primary input.

## Reading a website

- Start from the home or work page. List every case study it links to.
- Read every case study up to eight. If there are more, read the eight the
  site itself puts first, because a reviewer would do the same, and say which
  ones were skipped.
- Also read the about page and any linked CV. They carry title, scope and
  dates that case studies often omit.
- If a browser tool that renders pages and takes screenshots is available,
  prefer it over plain fetching for visual assessment. Plain fetching returns
  text and markup only, so visual quality must then be marked as not assessed.

## Verifying what you read

<!--
  Added after testing: a fetch tool that summarises pages reported a target
  role that was not on the page, and reported real images as placeholders
  because of their alt text. Errors like these flow straight into ratings
  and red flags unless checked.
-->

- **Summaries can be wrong.** Some fetch tools return a model-written summary,
  not the page. Before a claim drives a rating, a red flag or a quoted
  number, check it against the raw page text, or the rendered page when a
  browser is available. If it cannot be checked, mark it low confidence.
- **Collapsed content counts.** Read accordions, tabs and "read more"
  sections. Their content is evidence. Whether it is hidden from a skimming
  reader is a separate finding for portfolio effectiveness.
- **Alt text is not content.** Alt text such as "Placeholder image" does not
  mean the image is a placeholder. Check whether real images load before
  concluding anything. Report poor alt text under hygiene.
- **Not rendered is not missing.** Scroll-reveal animations and lazy-loaded
  images can render blank in a background or headless browser. Try disabling
  animations or scrolling slowly. Anything still not rendered is "not seen",
  never "missing" or "empty".
- **Cross-check numbers across pages.** Compare figures on the home, about
  and case study pages (team sizes, reports, dates, metrics). Note
  discrepancies; see evidence-rules.md for how to treat them.

## Sources that usually cannot be read

<!--
  Maintainers: update this list as tools change. It reflects plain web fetching
  as of late 2026. A browser-capable environment may read some of these.
-->

| Source | Typical problem | What to ask for |
| --- | --- | --- |
| pitch.com, Google Slides, Keynote links | Content is rendered client side; fetch returns little or nothing | PDF export |
| Figma, FigJam, Figma prototypes | Canvas content is not readable as text | PDF export or screenshots of key frames |
| Notion pages | Often partial; toggles and embeds missing | PDF export |
| Readymag, heavy WebGL or scroll-driven sites | Content loads on scroll or in canvas | PDF export or screen recording frames |
| Password-protected pages | Cannot be entered | PDF export. Never ask for or enter the password |
| Behance, Dribbble | Mostly images with little text; often rate-limited | Original case study or PDF |
| Video (Vimeo, YouTube, MP4, Lottie) | Cannot be watched | A short description from the designer of what the video shows, if self-assessing |

When a source cannot be read, say so in the Inputs section of the report and
continue with what was read. Do not guess the missing content.

## What can and cannot be assessed

**Can be assessed from text:** story structure, problem framing, stated role,
scope, methods, metrics, trade-offs, writing quality, positioning.

**Can be assessed from page images (PDF pages, screenshots, rendered pages):**
hierarchy, layout, typographic control, consistency across screens, whether
states and edge cases are shown, whether process artifacts are real or
decorative, density and scannability.

**Can be detected but not evaluated:** motion and video. The review can state
that motion or video is present, where it sits in the story, and what it is
labelled as showing (an interaction, a prototype, a transition, a brand
film). It cannot judge timing, easing, feel or emotional effect. Say so
plainly rather than praising or criticising motion it has not seen.

**Cannot be assessed:** anything not in the portfolio. Interview performance,
references, actual code quality behind a "coded prototype" link unless the
repo is public and read.

## Inputs record

Every report opens with a short record of what was read:

- Format and source (URL or file name)
- Pages or case studies read, and any skipped with the reason
- Visual assessment: full (images seen), partial, or none (text only)
- Context the user supplied (target level, JD, mode, intended image)

This lets the reader discount the review correctly. A text-only review of a
visual designer's portfolio is a partial review and must say so.
